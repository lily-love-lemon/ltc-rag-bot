## 三、发现的缺陷与修复（每步：现象 → 根因 → 改动 → 验证）

### P0-1 · Portal 生产模式鉴权链路断了（最严重）

- **现象**：生产模式（`API_KEY=<API_KEY>`）下，Portal 页面所有请求都会 401 —— 页面打不开数据、上传、切片全废。
- **根因**：双向断链。
  1. `app.py::_render_portal_html()` 会把 HTML 里的 `{{AUTO_API_KEY}}` 换成真 Key，但 **`portal/index.html` 里根本没有这个占位符**（ripgrep 确认 0 处），替换是空操作；
  2. 前端第 334 行写死 `const API_KEY = ''`，且 `指标/上传` 链路无人给它赋值。
  3. 设计规范 `Portal设计规范.md` 明确要求 Header 有 `[API Key]` 输入框 —— 实际 HTML 里也没有。
- **改动**（2 处，共 3 行）：
  - `portal/index.html:335`：`const API_KEY = '';` → `const API_KEY = '{{AUTO_API_KEY}}';`（恢复后端注入链路，dev 模式注入空串）
  - `portal/index.html:342`：新增 `authOnly()` helper —— multipart 上传**不能**带 `Content-Type: application/json`（会覆盖浏览器生成的 boundary），所以单独给一个只带鉴权头的函数
  - `portal/index.html:521`：`/ingest` 的裸 `fetch` 补上 `headers: authOnly()`，并补 `if (!r.ok) throw`（原代码不看状态码，401 也会当成功）
- **验证**：
  ```
  开发模式：未替换占位符=0  → ✅ 注入空串（后端跳过鉴权）
  生产模式：未替换占位符=0  → ✅ 已注入真实 API Key
  生产模式 /kb 无 key → HTTP 401 ✅ ；带正确 key → HTTP 200 ✅
  ```

### P0-2 · `/query` 把 `use_rerank` 参数丢了

- **现象**：Portal 上的「重排开关」是摆设，关掉也照跑重排。`项目汇总.md` 声称「/query 支持 use_rerank」，实际不支持。
- **根因**：`app.py::query()` 只透传了 `top_k` 与 `use_bm25`，`body.get("use_rerank")` 从未读取（`_do_rag` 有该形参，但路由层没传）。
- **改动**（1 行）：`app.py:1300` 补 `use_rerank=body.get("use_rerank", True),`
- **验证**：`use_rerank=false` → 响应 `hybrid.use_rerank=False` ✅（修复前恒为 True）

### P0-3 · 瘦身 prompt 被旧文件反覆盖

- **现象**：踩坑 1.6 记录「已把 FABE prompt 瘦身、去掉显式段落名」，但实际输出仍会带 `**Feature:**` 这类冗余标题，输出偏长（200–400 字）。
- **根因**：`_get_prompt()` 的逻辑是**文件优先**：`prompts/fabe.txt` 存在就用文件。而仓库里的 `fabe.txt` 还是 **V3 冗长版**（要求 FABE 四段标题、200–400 字）。`app.py` 内置的瘦身版只在文件缺失时才生效 → 修复事实上被架空。
- **改动**：`prompts/fabe.txt` 对齐为瘦身版：去掉显式段落名标注、字数收紧到 150–250、保留拒答规则（`知识库暂未收录相关内容`）。16 行 → 14 行。
- **验证**：实跑 `/query` 两次，回答 255 / 309 字，无 `**Feature:**` 型标题，落在 150–250 目标区间（首次略超因模型自由度，可后续用 prompt 再收紧）。

### 体验/一致性 · 旧 metadata 补字段脚本

- **现象**：线上 207 条切片仍是旧 schema（只有 `id/text/source/strategy`），导致 `/kb` 的 `by_type` 只剩 `['.inline']`，Portal「文件管理」tab 无法按类型/时间归类。
- **改动**：新增 `code/scripts/upgrade_metadata.py`（纯标准库，**幂等**）
  - 补 `created_at` / `file_type` / `file_size`
  - 老数据没有真实入库时间 → 用 `metadata.json` 自身 mtime 作为代理值，并置 `created_at_inferred: true` **显式标注是推断值**（不假装精确）
  - 落盘前自动备份 `metadata.json.bak-<UTC>`；原子写入；只补字段，**不动 `vectors.npy` / `vocab.json`**
  - 支持 `--dry-run`；写完自校验「vectors.npy 哈希未变」+「二次运行 0 变更」
- **验证**（用 207 条仿真旧数据）：补全 207 条 → 备份成功 → `vectors.npy` 哈希未变 → 幂等复查 0 变更 ✅；`by_type` 从 `['.inline']` 变为 `{'.md':203, '.inline':3, '.txt':1}` ✅
- **⚠️ 尚未在云端执行**：本地没有那份真实 `metadata.json`，需你授权 `tcb login` 后执行（下方命令）。
