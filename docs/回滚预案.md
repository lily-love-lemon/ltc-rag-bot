## 五、上一版脚本的致命缺陷（v2 已修复，务必留档）

### ⚠️ 假回滚 —— 最危险的一类

v1 的默认回滚目标是 `v3-20260918-smoke-green`，而**该 tag 在交接后的仓库里根本不存在**
（交接包不含 `.git`，Trae 的 tag 全部丢失）。于是：

```
git rev-parse v3-20260918-smoke-green   → 失败
→ 只打印一句「⚠️ 不是有效的 git tag/commit，跳过 git」
→ 继续执行 tcb cloudrun deploy --force   ← 部署的是【当前新代码】
→ 最后打印「✅ 回滚部署完成」
```

**运维以为回滚了，实际线上跑的还是出问题的新版本，而且状态显示"回滚完成"。**
故障期间的恢复窗口被这次假回滚直接吃掉。

**v2 的修法**：git 目标无效 → `die` 直接中止（exit 2），并列出所有可用 tag；只有 `--deploy-id` 时也拒绝执行（除非显式 `--allow-deploy-id-only`，因为 CloudBase 无灰度，仅切版本号仍会重新构建**当前代码**）。

### 其它 3 个缺陷

| # | 缺陷 | 后果 | v2 修法 |
|---|---|---|---|
| 2 | `git checkout <tag>` 留下 detached HEAD，不提示如何回去 | 下次提交可能落在游离 HEAD 上，提交丢失 | 显式 `--detach` + 打印 `git checkout <原分支>` 收尾提示 |
| 3 | 工作区有未提交改动时 checkout 中途失败 | 半残状态，代码处于"一半旧一半新" | 检出前检查，脏树直接拒绝（exit 3） |
| 4 | 回滚后只 grep 部署状态，不探活 | 「部署完成」不等于「服务可用」 | 增加 `/health` + `/kb` 探活，失败给 exit 5 |

### 另一个隐蔽陷阱：脚本自覆盖

`code/rollback.sh` 本身是 git 跟踪文件。回滚到旧 tag 时**它自己也被替换掉**，
而 bash 是「边读边执行」脚本的 —— 运行中的脚本被改写可能导致读到新旧混合内容、静默跑错逻辑。

**v2 修法**：脚本启动时先把自身复制到临时文件，再 `exec` 副本继续跑，使运行中的代码与磁盘解耦。
离线演练已覆盖此场景：回滚过程中 `rollback.sh` 确实被换回旧版，流程仍正常跑完。

## 六、离线演练（不碰线上即可验证本预案）

```bash
cd "<项目根>/code"
bash scripts/deploy_drill.sh            # 13 条断言，约 10 秒
bash scripts/deploy_drill.sh --keep     # 保留临时目录便于排查
```

原理：`git clone` 临时副本（带全 tag）→ 用 stub 版 `tcb` 替换 CLI（只记录调用、不联网）→
按 6 个场景跑真实脚本并断言行为。

| 场景 | 断言 |
|---|---|
| 无效目标 | 必须中止（exit 2），且**未发起任何部署** |
| 有效 tag | 流程跑完（exit 0）+ `app.py` 文件级回到旧版 + 自身被换掉仍正常 |
| 只给 `--deploy-id` | 必须拒绝（exit 2） |
| `deploy.sh --preflight-only` | 只检查不部署 |
| `deploy.sh` 非交互（stdin 关闭） | 退出码 0，可无人值守 |
| 部署命令形式 | 必须是 `-s <service> -e <env> --force`，且无 `--servicePath` 混用 |

**实测结果：13 通过 / 0 失败**（修复前基线：5 通过 / 4 失败）。
